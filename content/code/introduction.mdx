There are thousands of LeetCode problems, but you don't need to solve thousands to be ready. Most interview questions are built from a **small set of patterns**. Once you can spot the pattern, you have a starting point for the solution, and the interview becomes a conversation about details instead of a search for an idea.

This course teaches those patterns one at a time. Every guide follows the same structure so you always know what's coming.

## How each guide works

1. **The idea.** What the pattern is and why it's faster than the obvious approach.
2. **When to use it.** The clues in a problem statement that point to this pattern.
3. **Worked problems.** Classic interview questions, each solved from brute force to optimal, with an interactive visualization and clean Python code.
4. **Complexity.** The time and space analysis you'll be asked for.

## Recommended order

The patterns build on each other, so if you're starting fresh, go in order:

| # | Pattern | Typical clue in the problem |
|---|---------|-----------------------------|
| 1 | [Two Pointers](/learn/code/two-pointers) | Sorted array, pairs, palindromes, in-place changes |
| 2 | [Sliding Window](/learn/code/sliding-window) | Contiguous subarray or substring with a constraint |
| 3 | [Binary Search](/learn/code/binary-search) | Sorted input, or "find the minimum value that works" |
| 4 | [Stack](/learn/code/stack) | Matching pairs, "next greater element", undo/nesting |
| 5 | [Fast & Slow Pointers](/learn/code/fast-slow-pointers) | Linked list cycles, finding the middle |

More patterns (intervals, heaps, trees, graphs, backtracking and dynamic programming) are on the way.

## How to practice

<Callout type="tip" title="Active recall beats re-reading">
After reading a guide, close it and solve the linked problems from scratch on LeetCode. If you get stuck for more than 20 minutes, come back, read only the next step of the walkthrough, and try again.
</Callout>

- **Say it out loud.** Explain your approach as you code, the way you would in an interview.
- **Start with brute force.** State it, give its complexity, then improve it. Interviewers want to see that progression.
- **Test with small inputs.** Walk through your code on a tiny example before declaring it done, just like the visualizations do.
- **Revisit after a few days.** Spaced repetition is what makes patterns stick.
